# 脚本参数说明

基线参数写在 `baseline.env` 中，由 `scripts/run_topdown.sh` 读取。配置项使用大写和下划线，vLLM 命令参数使用小写和连字符。

例如，配置文件中写 `MAX_MODEL_LEN=16384`，脚本启动服务时会传入 `--max-model-len 16384`。以下列出两者的对应关系，基线值以 Qwen3 示例为准。

## 1. 基础配置项

| 配置项 | 基线值 | 含义 |
| --- | --- | --- |
| `CHIP` | `920b` | 选择 PMU 平台，可用 `920b`、`950`、`hygon_c86_7490` 或 `zen4` |
| `PROJECT` | `/home/fj/vllm_topdown_persistent` | 采集代码目录，宿主机与容器内路径需一致 |
| `CONTAINER` | `topdown_920b` | 执行采集的 Docker 容器名 |
| `MODEL` | `/home/model/Qwen3-8B-Instruct` | 模型权重、配置和 tokenizer 目录 |
| `MODEL_SHORT` | `qwen3` | 输出工作簿使用的模型标签 |
| `PYTHON_BIN` | `/opt/vllm/bin/python3` | 容器内执行采集脚本的 Python |
| `VLLM_BIN` | `/opt/vllm/bin/vllm` | 容器内的 vLLM 命令 |
| `VLLM_SITE` | 留空 | vLLM 安装目录，留空时由 Python 自动查找 |
| `VLLM_VERSION` | `0.26.0` | 写入运行记录的版本标签 |
| `VLLM_VERSION_SHORT` | `0.26` | 输出工作簿文件名中的版本标签 |
| `GPU_ID` | `0` | 容器内 GPU 编号，通过 `CUDA_VISIBLE_DEVICES` 传给服务和客户端 |
| `VLLM_USE_V2_MODEL_RUNNER` | `1` | 使用 V2 Model Runner |

## 2. vLLM 服务端参数

| 对应配置项 | vLLM 参数 | 基线值 | 含义 |
| --- | --- | --- | --- |
| `MODEL` | 模型路径（位置参数） | `/home/model/Qwen3-8B-Instruct` | 加载指定模型 |
| `SERVED_MODEL` | `--served-model-name` | `qwen3-8b` | API 对外提供的模型名 |
| `SERVER_HOST` | `--host` | `127.0.0.1` | 服务监听地址 |
| `PORT` | `--port` | `18026` | 服务监听端口 |
| `TENSOR_PARALLEL_SIZE` | `--tensor-parallel-size` | `1` | 张量并行度 |
| `DATA_PARALLEL_SIZE` | `--data-parallel-size` | `1` | 数据并行度 |
| `MAX_MODEL_LEN` | `--max-model-len` | `16384` | 单条请求的最大序列长度，包括输入和输出 token |
| `MAX_NUM_SEQS` | `--max-num-seqs` | `1` | 一次调度允许处理的最大序列数 |
| `MAX_NUM_BATCHED_TOKENS` | `--max-num-batched-tokens` | `16384` | 一次调度的 token 预算 |
| `GPU_MEMORY_UTILIZATION` | `--gpu-memory-utilization` | `0.8` | vLLM 的 GPU 内存使用比例配置 |
| `BLOCK_SIZE` | `--block-size` | `16` | 每个 KV Cache block 的 token 数 |
| `DTYPE` | `--dtype` | `bfloat16` | 推理数据类型 |
| `SERVER_SEED` | `--seed` | `0` | 服务端随机种子 |
| `PREFIX_CACHING_FLAG` | `--no-enable-prefix-caching` | 启用该选项 | 关闭 Prefix Cache |
| `SERVER_FLAGS` | `--no-async-scheduling` | 启用该选项 | 关闭异步调度 |
| `PLACEMENT_MODE=worker_set` 时由脚本添加 | `--distributed-executor-backend` | `mp` | 使用多进程执行器 |
| `PLACEMENT_MODE=worker_set` 时由脚本添加 | `--numa-bind` | 启用该选项 | 按指定 CPU 和 NUMA 节点放置 Worker |
| `WORKER_NUMA_NODE` | `--numa-bind-nodes` | `1` | Worker 内存所在 NUMA 节点 |
| `WORKER_CPUS` | `--numa-bind-cpus` | `92,94` | Worker 使用的逻辑 CPU |

`MAX_NUM_BATCHED_TOKENS=16384` 由基线示例显式设置，公共配置值为 `163840`。CPU 编号为 84 示例，其他机器按实际拓扑填写。

## 3. Benchmark 客户端参数

| 对应配置项 | vLLM 参数 | 基线值 | 含义 |
| --- | --- | --- | --- |
| `BENCH_BACKEND` | `--backend` | `openai` | 通过 OpenAI 兼容接口发送请求 |
| `SERVER_HOST`、`PORT` | `--base-url` | `http://127.0.0.1:18026` | vLLM 服务地址 |
| `BENCH_ENDPOINT` | `--endpoint` | `/v1/completions` | 请求的 API 路径 |
| `SERVED_MODEL` | `--model` | `qwen3-8b` | 请求中的模型名，需与服务端名称一致 |
| `MODEL` | `--tokenizer` | `/home/model/Qwen3-8B-Instruct` | Benchmark 使用的 tokenizer 路径 |
| `DATASET_NAME` | `--dataset-name` | `random` | 使用随机生成的数据集 |
| `RANDOM_INPUT_LEN` | `--random-input-len` | `7000` | 每个请求的目标输入长度，单位为 token |
| `RANDOM_OUTPUT_LEN` | `--random-output-len` | `100` | 每个请求的目标输出长度，单位为 token |
| `RANDOM_RANGE_RATIO` | `--random-range-ratio` | `0` | 长度变化比例，`0` 表示固定目标长度 |
| `NUM_PROMPTS` | `--num-prompts` | `1` | 每轮发送的请求数 |
| `NUM_WARMUPS` | `--num-warmups` | `0` | Benchmark 自身的预热请求数 |
| `READY_CHECK_TIMEOUT_SEC` | `--ready-check-timeout-sec` | `0` | Benchmark 内置就绪检查的等待秒数，`0` 表示跳过 |
| `MAX_CONCURRENCY` | `--max-concurrency` | `1` | 同时进行的最大请求数 |
| `REQUEST_RATE` | `--request-rate` | `1` | 请求发送速率，单位为请求/秒 |
| `IGNORE_EOS_FLAG` | `--ignore-eos` | 启用该选项 | 生成时忽略 EOS，按目标输出长度继续生成 |
| `TEMPERATURE` | `--temperature` | `0` | 生成采样温度，`0` 为贪心采样 |
| `BENCH_SEED` | `--seed` | `0` | Benchmark 输入生成的随机种子 |

服务启动阶段由采集脚本单独检查服务就绪。修改请求数、输出长度或 CUDA Graph 模式后，需重新核对有效 Decode 样本数。

## 4. 绑核与 NUMA 配置

| 配置项 | 84 基线示例 | 含义 |
| --- | --- | --- |
| `PLACEMENT_MODE` | `worker_set` | 启用显式 Worker、服务和客户端绑核 |
| `WORKER_POOL_CPUS` | `88,90,92,94` | 可供 Worker 选择的四个物理核 |
| `WORKER_CPUS` | `92,94` | Worker 实际使用的两个物理核 |
| `WORKER_NUMA_NODE` | `1` | Worker CPU 与匿名内存所在的 NUMA 节点 |
| `SERVICE_CPUS` | `256,258` | API Server 和 EngineCore 的 CPU 集合 |
| `API_CPUS` | `256` | API Server 使用的 CPU |
| `ENGINE_CPUS` | `258` | EngineCore 使用的 CPU |
| `CLIENT_CPUS` | `264` | Benchmark 客户端使用的 CPU |

Worker 核池需位于同一 socket、cluster 和 NUMA 节点，每个物理核选择一个逻辑 CPU。Worker 可使用核池中的 1、2 或 4 个核。服务和客户端使用独立物理核。Zen 4 通过共享 L3 的 CPU 集合识别 cluster。

## 5. 采集配置

| 配置项 | 基线值 | 含义 |
| --- | --- | --- |
| `COLLECTION_PROFILE` | `full` | 采集完整阶段；920B、950、Zen 4 支持 `end_to_end` 仅采父阶段 |
| `GROUP_SET_920B` | `extended` | 920B 使用 22 组 PMU；`standard` 为 13 组 |
| `ZEN4_L3_ENABLE` | Zen 4 示例为 `1` | 启用 Zen 4 共享 L3 事件组 |
| `HOTSPOT_SCOPE` | `thread` | 热点采样对象为 Worker 主执行线程，`worker` 表示 Worker 进程 |
| `PERF_EVENT` | `cycles:u` | CPU 热点采样事件 |
| `PERF_PERIOD` | `100000` | 每隔指定事件次数采样一次 |
| `SPE_ENABLE` | `0` | Arm SPE 采样开关，启用时需准备宿主机采样配置 |
| `ANON_THP_MODE` | `off` | 使用 `thp_exec` 关闭服务进程匿名透明大页 |
| `FREQUENCY_ENABLE` | `0` | 是否增加独立频率观察轮，启用需配套 DevKit |
| `DEVKIT_BIN` | `devkit` | 独立频率观察使用的 DevKit 路径 |
| `GROUP_START_TEMPERATURE` | `0` | 各组采集前的 GPU 温度门槛，单位为 °C，`0` 表示不等待降温 |
| `ROUND_WARMUPS` | `1` | 采集流程额外发出的预热请求数 |
| `WARMUP_SCOPE` | `session` | 外层预热按服务会话执行，`per_group` 表示每组执行 |
| `PERSISTENT_BENCH_CLIENT` | `1` | 保留 Benchmark 客户端并复用准备好的输入 |

Zen 4 可选 L3 组适用于已验证的 AMD Family 19h Model 11h。Worker 需使用同一 L3 域内 1–2 个物理核的首个硬件线程。其他型号或拓扑将 `ZEN4_L3_ENABLE` 设为 `0`。Zen 4 当前入口使用 `FREQUENCY_ENABLE=0`。

## 6. 各平台采集范围

| 平台 | 阶段 | PMU 组 | 前后独立 Benchmark |
| --- | --- | --- | --- |
| 920B | 父阶段 + 八阶段 | 13 或 22 | 22 组模式有 |
| 950 | 父阶段 + 八阶段 | 13 | — |
| 海光 7490 | 八阶段 | 11 个 Core 组 + 1 个共享 L3 组 | — |
| Zen 4 | 父阶段 + 八阶段 | 14 个 Core 组，可加 1 个共享 L3 组 | 有 |
