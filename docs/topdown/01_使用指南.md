# 使用指南与参数参考

这套代码通过 vLLM 在线推理请求驱动 CPU 阶段测量，可采集阶段耗时、PMU 计数、CPU 热点和 Arm SPE。请求性能由 vLLM Benchmark 统计，阶段性能由服务端插桩采集；二者的范围不同。

本手册中的路径相对于采集代码根目录。`/path/to/...`、`<...>` 是待替换值；CPU、NUMA、GPU 和模型参数须按实际环境填写。算子级 ReadCoreCycle 使用单独的算子插桩代码，见 [PMU 指标与计时说明](03_PMU与计时.md)。

## 1. 准备完整代码和运行环境

采集代码至少包含以下文件，不能只复制一个启动脚本：

| 文件或目录 | 用途 |
| --- | --- |
| `scripts/config.env` | 公共参数和芯片事件组 |
| `scripts/run_topdown.sh`、`scripts/run_one.sh` | 整体采集与单轮执行 |
| `scripts/session.sh`、`scripts/bench_client.py` | 常驻服务和常驻请求客户端 |
| `kperf_instrument.py`、配套 `vllm/` 源码 | 阶段打点、PMU 控制和运行时覆盖 |
| `scripts/<CHIP>/` | 芯片采集流程、指标计算与报表定义 |
| `scripts/parse_run.py`、`scripts/build_xlsx.py` | 原始记录解析与工作簿生成 |
| `scripts/placement.py`、`scripts/placement.sh` | 线程与 NUMA 放置 |
| `scripts/run_experiment.sh`、`scripts/spe/`、`scripts/pages/` | 受控放置、SPE、页面检查与监督 |

需要 Linux、可用的 GPU 推理环境、与插桩源码匹配的 vLLM/PyTorch、Docker、Bash、`numactl`、`perf`。Arm SPE 另外要求处理器、内核和 perf 支持 SPE。仅导出报表不需要 GPU。

宿主侧 Python 与容器侧 Python 分开配置。宿主负责监督、SPE 解码和文件检查；容器负责推理、Benchmark 和阶段数据处理。不要因为一侧能导入依赖，就认为另一侧也已安装。

在代码根目录准备宿主报表环境：

```bash
uv venv .host_venv
uv pip install --python .host_venv/bin/python \
  -r scripts/requirements-report.txt regex
```

容器应已安装匹配的推理环境，并能导入 `openpyxl`、`regex` 及 vLLM Benchmark 依赖。`requirements-report.txt` 固定 `openpyxl==3.1.5`。常驻客户端依赖配套的 `prepare_benchmark()` 和 `main_async()` 接口，不能用任意版本的上游安装包替代配套源码。

配置、代码、模型和结果目录必须在容器中可访问。当前脚本直接把绝对路径传入容器，代码、配置和结果目录应使用相同路径挂载。检查：

```bash
docker inspect "$CONTAINER" --format \
  '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
docker exec "$CONTAINER" test -f "$PROJECT/scripts/$CHIP/run.sh"
docker exec "$CONTAINER" test -d "$MODEL"
docker exec "$CONTAINER" "$PYTHON_BIN" -c \
  'import sys, torch, vllm, openpyxl, regex; print(sys.executable); print(vllm.__file__); print(torch.__version__)'
```

以上变量由下一节的配置提供。路径检查通过只证明文件可见；正式运行仍需检查 `runtime.txt` 和实际加载的源码、动态库。

## 2. 编写测试配置

创建 `configs/test.env`，只写需要覆盖的参数。配置按 Bash 文件加载，应使用可信内容。不要把公共 `config.env` 的末尾加载逻辑复制到测试配置中。

```bash
# configs/test.env
CHIP=920b
PROJECT=/path/to/collector
CONTAINER="<container_name>"
MODEL=/path/to/model
MODEL_SHORT="<model_label>"
SERVED_MODEL="<api_model_name>"
PYTHON_BIN=/path/in/container/to/python
VLLM_BIN=/path/in/container/to/vllm

GPU_ID=0
PORT=18026
COLLECTION_PROFILE=full
SPE_ENABLE=0
VLLM_USE_V2_MODEL_RUNNER=1
SERVER_FLAGS="--no-async-scheduling"
PREFIX_CACHING_FLAG=--no-enable-prefix-caching

# 以下是功能检查的示例负载，不是性能结论的固定负载。
RANDOM_INPUT_LEN=128
RANDOM_OUTPUT_LEN=16
MAX_MODEL_LEN=2048
MAX_NUM_SEQS=1
MAX_CONCURRENCY=1
NUM_PROMPTS=1
NUM_WARMUPS=0
ROUND_WARMUPS=1
WARMUP_SCOPE=session
PERSISTENT_BENCH_CLIENT=1
TEMPERATURE=0
IGNORE_EOS_FLAG=--ignore-eos
```

运行前把所有 `<...>` 和路径占位符替换为实际值。先选取短负载检查请求成功、阶段完整和结果文件，再改成目标负载。

公共 `scripts/config.env` 先设置默认值，再加载 `TOPDOWN_CONFIG` 指定的测试配置。部分公共值是直接赋值，所以**把要固定的参数写入测试配置**，不要仅依赖启动命令前临时设置的环境变量。

需要在当前 shell 执行前置检查或离线汇总时，先从代码根目录加载同一配置，使示例中的变量具有实际值：

```bash
export TOPDOWN_CONFIG="$(pwd -P)/configs/test.env"
set -a
source scripts/config.env
set +a
```

## 3. 执行一次采集

在 Linux 宿主、采集代码根目录执行：

```bash
CODE_ROOT="$(pwd -P)"
CONFIG="$CODE_ROOT/configs/test.env"
RESULT="$CODE_ROOT/results/test_01"
bash scripts/run_topdown.sh "$CONFIG" "$RESULT"
```

结果目录使用新目录。普通运行不会覆盖已有结果。`full` 保留父阶段、八阶段及热点；Arm 的 `end_to_end` 仅选择父阶段测量，跳过内部八阶段和热点。关闭 SPE 应设置 `SPE_ENABLE=0`，不需要缩小阶段采集范围。

Hygon 代码包须同时包含父阶段采集、汇总及工作簿支持：检查 `hygon_c86_7490/run.sh`、`summary.py` 和 `build_xlsx.py` 均识别 `execute_model_to_sample_tokens`，再按父阶段加八阶段验收。

脚本启动服务后，在同一个服务生命周期内切换 time、PMU 组和热点。常驻客户端提前准备请求输入，再按采集轮次发起请求：

```text
启动并预热服务 → 准备客户端输入 → time 轮 → 各 PMU 组
                                      → 热点／频率轮 → 关闭并生成结果
```

`bench_client.py` 调用 `vllm.benchmarks.serve` 的在线请求与统计实现。它并不绕过 HTTP，也不是 GPU Kernel 微基准。

需要显式 Worker 放置、页面检查或 SPE 时，补齐第 5 节的参数，然后执行：

```bash
bash scripts/run_experiment.sh "$CONFIG" "$RESULT"
```

该命令要求 `PLACEMENT_MODE=worker_set`，并要求宿主 Python、锁路径、子进程回收工具和二进制保留目录。直接调用时应在配置中显式写 `COLLECTION_PROFILE` 和 `SPE_ENABLE`，不要依赖其默认行为。SPE 的完整设置见 [采样与 Trace 指南](04_采样与Trace.md)。

### 扩展 PMU 采集

提供 `scripts/920b/run_missing.sh` 且 `run_experiment.sh` 实现 `RUN_EXTRA` 分支的代码包，支持 22 组扩展采集：

```bash
RUN_EXTRA=1 bash scripts/run_experiment.sh "$CONFIG" "$RESULT"
```

配置仍写 `COLLECTION_PROFILE=full`；外层监督器将本次任务识别为 `extra`。这条流程采集父阶段、八阶段、扩展 PMU、time、频率和前后两次干净 Benchmark，**不采热点和 SPE，也不自行生成完整工作簿**。它与普通 `full` 的覆盖范围不同。需要完整交付时，应使用代码包配套的验证、汇总程序，并单独安排热点／SPE；不能把 `extra` 结束当作所有采集项目完成。

## 4. 请求与服务参数

下表的“默认”来自公共配置；正式比较应在测试配置中显式固定关键项。

| 参数 | 含义／单位 | 默认或约束 |
| --- | --- | --- |
| `CHIP` | PMU 平台选择 | `920b`、`950`、`hygon_c86_7490`，须与实际 CPU 匹配 |
| `MODEL` / `MODEL_SHORT` / `SERVED_MODEL` | 模型路径／文件名标签／API 模型名 | 三者用途不同；请求中的模型名须与服务一致 |
| `VLLM_SITE` | 被覆盖的 vLLM 安装目录 | 留空时用容器解释器查询 |
| `VLLM_USE_V2_MODEL_RUNNER` | Runner 选择 | `1`；本套八阶段依赖相应插桩路径 |
| `GPU_ID` | 可见 GPU 选择 | `0`；与设备拓扑一起检查 |
| `SERVER_HOST` / `PORT` | API 地址／端口 | `127.0.0.1` / `18026`；检查端口可用 |
| `TENSOR_PARALLEL_SIZE` / `DATA_PARALLEL_SIZE` | TP／DP 并行度 | 均为 `1`；多 Worker 不自动获得完整线程覆盖 |
| `DTYPE` | 推理数据类型 | `bfloat16`；受模型和量化实现约束 |
| `BLOCK_SIZE` | KV block 大小 | `16` |
| `MAX_MODEL_LEN` | 服务最大序列长度，token | 公共配置 `16384`；须容纳目标请求 |
| `MAX_NUM_SEQS` | 服务端同时处理的序列上限 | `1`，不等于客户端并发数 |
| `MAX_NUM_BATCHED_TOKENS` | 每次调度的 token 预算 | 公共配置 `163840`；可改变 Prefill 调度方式 |
| `GPU_MEMORY_UTILIZATION` | GPU 内存使用比例 | `0.8` |
| `SERVER_FLAGS` | 追加服务参数 | 公共配置为 `--async-scheduling`；对照中显式选开／关 |
| `PREFIX_CACHING_FLAG` | Prefix cache 开关 | `--no-enable-prefix-caching` |
| `SERVER_SEED` / `BENCH_SEED` | 服务／输入生成随机种子 | 均为 `0` |
| `BENCH_BACKEND` / `BENCH_ENDPOINT` | 请求协议和路径 | `openai` / `/v1/completions` |
| `DATASET_NAME` | Benchmark 数据集类型 | `random` |
| `RANDOM_INPUT_LEN` / `RANDOM_OUTPUT_LEN` | 输入／输出 token 数 | 公共配置 `7000` / `100`；可覆盖 |
| `RANDOM_RANGE_RATIO` | 随机长度范围比例 | `0`，固定目标长度 |
| `NUM_PROMPTS` | 每个 Benchmark 调用的请求数 | `1`；当前阶段对齐流程以单请求为基准 |
| `MAX_CONCURRENCY` | 客户端最大并发 | `1` |
| `REQUEST_RATE` | 客户端请求率，请求/秒 | `1`；单请求不构成吞吐压力扫描 |
| `IGNORE_EOS_FLAG` | 是否忽略提前 EOS | `--ignore-eos`，便于固定输出长度 |
| `TEMPERATURE` | 采样温度 | `0`；固定条件比较应保持一致 |
| `NUM_WARMUPS` | vLLM Benchmark 自身预热次数 | `0` |
| `ROUND_WARMUPS` | 外层采集预热请求数 | 公共配置 `0`；与 `NUM_WARMUPS` 分开 |
| `WARMUP_SCOPE` | 外层预热发生范围 | `per_group` 或 `session`；分别为每组或服务会话一次 |
| `PERSISTENT_BENCH_CLIENT` | 保留客户端与已生成输入 | 执行器默认 `1` |

修改 `NUM_PROMPTS`、并发、输出长度或 Graph 模式后，需要重新核对有效调用数量。默认解析使用 `RANDOM_OUTPUT_LEN - 1` 作为单请求 Decode 数，不能仅增加请求数就假定解析器已适配。

## 5. 采集与放置参数

| 参数 | 用途 | 使用规则 |
| --- | --- | --- |
| `COLLECTION_PROFILE` | 采集范围 | 显式选 `full`；仅父阶段时才选 `end_to_end` |
| `SPE_ENABLE` | Arm SPE | 写 `0` 或 `1`；公共入口另支持 `auto`，可复现实验不依赖自动选择 |
| `PLACEMENT_MODE` | CPU/NUMA 放置 | `worker_set` 为显式 Worker 集合 |
| `WORKER_CPUS` | Worker 允许的逻辑 CPU | 从核池选取；物理核与 SMT 关系先确认 |
| `WORKER_POOL_CPUS` | 候选物理核池 | 当前校验器要求四个物理核、每核一个逻辑 CPU |
| `WORKER_NUMA_NODE` | Worker 内存放置节点 | 分离放置实现中不一定等于 Worker 所在 CPU 节点 |
| `WORKER_CPU_NODE` | Worker CPU 节点 | 仅分离放置实现使用；须与 CPU 集合一致 |
| `SERVICE_CPUS` / `CLIENT_CPUS` | 服务进程／客户端 CPU | 与 Worker 分工明确 |
| `API_CPUS` / `ENGINE_CPUS` | API／Engine 独立角色 CPU | 需要配套分角色放置实现；两者的并集对应服务 CPU 集合 |
| `HOTSPOT_SCOPE` | 热点统计对象 | `thread` 为主执行线程，`worker` 为 Worker 进程范围 |
| `PERF_EVENT` / `PERF_PERIOD` | 热点事件／事件周期 | `cycles:u` / `100000`；周期不是采样时长 |
| `FREQUENCY_ENABLE` / `DEVKIT_BIN` | 独立频率观察轮 | 默认 `0` / `devkit`；开启不代表已经锁频 |
| `HOST_PYTHON` | 宿主工具解释器 | 如代码目录下 `.host_venv/bin/python` 的绝对路径 |
| `SUBREAPER_BIN` | 子进程回收工具 | 可执行的 `docker-init` 或兼容 `tini` |
| `EXPERIMENT_LOCK` | 互斥锁文件 | 竞争同一资源的任务使用同一个锁 |
| `SPE_BINARY_CACHE` | 与采样匹配的 ELF 保留目录 | 用于地址解析和重解码 |
| `CODE_PAGE_CONDITION` / `CODE_PAGE_MODE` | 预先准备的代码页条件／`4k` 或 `64k` | 配置文字必须对应实际页检查 |
| `CODE_PAGE_NUMA_NODE` | 独立代码页节点 | 需要支持分离放置的监督器 |
| `ANON_THP_MODE` | 匿名页 THP 条件 | 需要配套进程内实现；见第二份文档 |
| `GROUP_START_TEMPERATURE` | 每组开始前的温度门槛 | `0` 表示不等待冷却；与异常温度上限不同 |
| `GPU_THERMAL_LIMIT` | 监督器温度上限 | 按配置指定；不要把温度控制当作已消除所有热状态差异 |

`API_FREQ_KHZ`、`ENGINE_FREQ_KHZ`、`WORKER_FREQ_KHZ`、`L3_WAYS` 等属于条件控制层。仅在配置里增加这些字段，不会让普通采集脚本自动设置频率或缓存。操作方法见 [测试方法与条件切换](02_测试方法.md)。

## 6. 检查结果和生成报表

| 文件 | 检查内容 |
| --- | --- |
| `commands.txt`、各轮 `run.env` | 实际展开后的命令和参数，而非计划值 |
| `runtime.txt`、身份记录 | Python、vLLM、PyTorch 与加载路径 |
| `service/` | 常驻服务日志、控制状态和客户端身份 |
| `<group>/measurement.log`、`<group>/parsed/` | 本轮测量记录及按阶段解析的原始行 |
| `end_to_end/` | 父阶段的独立 time／PMU 请求 |
| `collection_quality.csv`、各轮质量文件 | 应有、选中、有效、无效样本数 |
| `summary.csv`、`*.xlsx` | 汇总与报告；只有生成报告的流程才有这些文件 |
| `hotspot/`、`frequency/`、`spe/` | 对应专项采集；未启用时不应假定存在 |
| `benchmark_before/`、`benchmark_after/` | 扩展流程中不打开测量的干净请求 |
| `evidence/`、完成／清理记录 | 实际身份、放置与资源恢复检查 |

常规流程自动解析和生成工作簿。需要离线重新生成时，在能读取结果且具备依赖的环境执行：

```bash
"$PYTHON_BIN" "scripts/$CHIP/summary.py" "$RESULT"
"$PYTHON_BIN" scripts/build_xlsx.py "$RESULT" \
  --config "scripts/$CHIP/report_config.json" --chip "$CHIP" \
  --version "$VLLM_VERSION_SHORT" --model-short "$MODEL_SHORT" \
  --input-len "$RANDOM_INPUT_LEN" --output-len "$RANDOM_OUTPUT_LEN" \
  --compact-report --include-end-to-end
```

此命令用于配套汇总器支持的结果结构。扩展 PMU 的附加指标和字段修正须使用其配套验证／导出逻辑；不能仅换一份 JSON 就宣称全部指标已进入报告。离线命令不会重新运行模型。

验收至少包括请求成功、实际 token 数、全部要求的阶段与事件组、原始计数有效性、条件前后不漂移，以及服务、采样器和控制资源已释放。看到一个 Excel 文件不等于这些检查都通过。

## 7. 常见问题与清理

| 现象 | 优先检查 |
| --- | --- |
| 容器内找不到脚本／模型 | `docker inspect` 挂载、同路径可见性、符号链接目标 |
| 启动后无有效阶段 | Runner、Graph 路径、插桩源码是否真正加载、服务启动错误 |
| PMU 打开失败 | 事件编码、平台支持、权限、可用计数器、其他计数器使用者 |
| `time_enabled != time_running` | 事件组无法持续调度；不要自动按比例放大后当作有效阶段结果 |
| 调用数与预期不符 | EOS、请求失败、预热混入、多请求、并发、Graph qualifier |
| 相同目录再次运行被拒绝 | 新建运行目录；只在明确支持恢复的流程使用恢复功能 |
| 热点为空／符号未知 | 目标 TID、采样周期、测量窗口、对应 ELF 和 Python 符号支持 |
| SPE 失败 | 见第四份文档的 AUX、线程和时间戳检查 |

正常退出由脚本回收本次服务、客户端和临时覆盖目录。中断后按保存的 PID、启动时间和运行目录检查残留，仅停止本次运行创建的进程。保留原始计数、Benchmark、配置、源码与二进制身份、验证结果；需重解码 SPE 时还要保留 `perf.data` 及配套 ELF。确认无人使用后再释放临时运行副本和重复归档，不用全局进程清理或全局缓存清空命令。
