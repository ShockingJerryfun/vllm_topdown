# 测试方法与条件切换

一次可比较的测试需要同时固定负载、运行实现和硬件条件。配置文件表达目标，运行时检查证明目标是否生效。基本运行方式见 [使用指南](01_使用指南.md)。

## 1. 先定义比较对象

为每个条件保存一份配置和一个新结果目录。先固定模型、权重与量化方式、vLLM/PyTorch、GPU、输入输出长度、请求数、并发、随机种子、预热策略，再改变目标因素。

| 比较因素 | 改变项 | 同时固定的关键项 |
| --- | --- | --- |
| Worker 核数 | `WORKER_CPUS` 的物理核数量 | 核池、频率、NUMA、其他角色放置 |
| CPU–GPU 距离 | Worker CPU 节点 | GPU、代码页和数据页位置；若也改变，应另列组合条件 |
| CPU–DRAM 距离 | Worker 数据页节点 | Worker CPU、代码页、GPU |
| 代码页位置 | `CODE_PAGE_NUMA_NODE` | Worker CPU、数据页节点、页大小 |
| 代码页大小 | `CODE_PAGE_MODE` | 文件字节、独立副本、位置和其他内存条件 |
| 匿名 THP | `ANON_THP_MODE` | 代码页条件及内存放置 |
| 频率 | 某个角色所属 CPUFreq policy | 其他角色频率、温度和请求 |
| 缓存分配 | L2／L3 控制值 | 频率、放置、模型、系统缓存模式 |
| Graph／异步调度 | 相应服务参数 | 其他编译与请求参数 |
| 编译优化 | Python或库的构建产物 | 源码、依赖、运行参数与硬件条件 |

把 Worker、代码页、DRAM 一起从近端移到远端，测到的是组合放置差异，不能只命名为“PCIe 距离影响”。

## 2. 设置 CPU 与 NUMA

### 2.1 查拓扑再选核

在目标 Linux 环境查询：

```bash
lscpu -e=CPU,CORE,SOCKET,NODE,ONLINE
numactl --hardware
nvidia-smi --query-gpu=index,pci.bus_id,name --format=csv
cat "/sys/bus/pci/devices/$GPU_BDF/numa_node"
```

`GPU_BDF` 使用完整 PCI 地址。返回 `-1` 表示内核未提供明确节点，不能自动当作节点 0。不要把相邻逻辑 CPU 编号直接当成不同物理核；检查 `thread_siblings_list` 和共享 Cache 列表。

显式配置的含义：

```bash
PLACEMENT_MODE=worker_set
WORKER_POOL_CPUS="<four_physical_cores>"
WORKER_CPUS="<selected_worker_cpus>"
WORKER_CPU_NODE="<cpu_node>"
WORKER_NUMA_NODE="<data_node>"
CODE_PAGE_NUMA_NODE="<code_node>"
API_CPUS="<api_cpus>"
ENGINE_CPUS="<engine_cpus>"
SERVICE_CPUS="<api_and_engine_cpus>"
CLIENT_CPUS="<client_cpus>"
```

该示例需要支持分角色、CPU／数据／代码节点分离的 `placement.py`、`numa_utils.py` 和监督器。普通绑定实现未读取的字段不会产生控制效果。当前 Worker 核池校验以四个物理核为边界，测试集合从其中选择 1、2 或 4 个核。

### 2.2 核验真正执行的线程

Worker 进程可能包含多个线程。`taskset -p` 只检查给定 PID/TID，不足以证明全部线程一致：

```bash
for task in /proc/"$WORKER_PID"/task/*; do
  tid="${task##*/}"
  taskset -pc "$tid"
done
cat "/proc/$WORKER_PID/numa_maps"
```

应同时检查 API、Engine、Worker 和客户端的实际身份、进程启动时间、线程集合及 affinity。配套放置器会检查 PID 复用和同一服务会话内的配置变化。

绑核与内存放置是两件事：修改 affinity 不会自动迁移已经分配的页面。内存策略应在加载器、模型及目标内存分配之前生效，随后用 `numa_maps`、页面检查和前后快照确认。

## 3. 控制 CPU 频率

`FREQUENCY_ENABLE=1` 开启独立频率观察轮，不执行锁频。`API_FREQ_KHZ` 等字段需要条件控制器消费；普通采集器不会仅凭字段名修改系统。

操作前查询目标 CPU 的 `cpufreq` policy、`related_cpus`、驱动、可用频率和 governor。多个 CPU 可能共用一个 policy，修改前要确认影响范围。[Linux CPUFreq 文档](https://docs.kernel.org/admin-guide/pm/cpufreq.html)

下面是支持 CPUFreq sysfs 时、对**已经选定且允许修改的一个 policy**设置上下限的命令模板。`POLICY`、`TARGET_KHZ` 和 `STATE` 由使用者设置，`STATE` 是本次新建的恢复记录目录：

```bash
mkdir -p "$STATE"
for key in scaling_governor scaling_min_freq scaling_max_freq; do
  cat "$POLICY/$key" > "$STATE/$key"
done
cat "$POLICY/related_cpus"
cat "$POLICY/cpuinfo_min_freq"
cat "$POLICY/cpuinfo_max_freq"

# 先确认 TARGET_KHZ 在硬件支持范围内。
cat "$POLICY/cpuinfo_min_freq" > "$POLICY/scaling_min_freq"
printf '%s\n' "$TARGET_KHZ" > "$POLICY/scaling_max_freq"
printf '%s\n' "$TARGET_KHZ" > "$POLICY/scaling_min_freq"
```

这些写操作需要相应权限。若平台不暴露 CPUFreq，不套用此模板；保留现有策略并报告实测频率。设置上下限后仍可能受到硬件热、功耗或固件限制，需在负载期间采样。

配套 `frequency.py` 运行 DevKit 的 `tuner turbostat`，由采集器在请求前等待 `frequency.ready`，请求后写 `frequency.stop`。输出包含每核 MHz 和角色汇总。它是独立请求的频率观察，不是每个 PMU 原始样本对应的即时频率。

测试结束按保存的原值恢复：先暂时降低最小值以避免上下限冲突，再恢复最大值、最小值和 governor，最后读回。恢复原始值，不写一个推测的“默认频率”。

## 4. 切换代码页与匿名页条件

### 4.1 文件代码页的准备

`4k`／`64k` 条件作用于选定可执行文件的实际 folio。它不把系统基础页改成 64KB，也不保证全部代码映射都是同一页大小。64KB 文件代码页依赖适配内核功能，普通匿名 THP 支持不能代替这一前提。

准备工具使用独立 inode 的相同字节副本，通过私有 mount namespace 覆盖新启动服务所见的路径。原有进程继续使用原挂载视图。

在目标 Linux 上编译工具；从代码根目录执行：

```bash
cc -O2 -Wall -Wextra -Werror -static \
  scripts/pages/namespace_exec.c -o scripts/pages/namespace_exec
cc -O2 -Wall -Wextra -Werror -static \
  scripts/pages/prefault.c -o scripts/pages/prefault
cc -O2 -Wall -Wextra -Werror -static \
  scripts/pages/process_pages.c -o scripts/pages/process_pages
```

在能正确解析模型运行环境文件路径的容器内准备条件。以下变量分别指 Python、当前服务 maps 快照、条件新目录、页模式、辅助进程 CPU 和代码页 NUMA 节点：

```bash
"$PYTHON_BIN" scripts/pages/prepare.py \
  --source-root / --maps "$MAPS_FILE" --output "$CONDITION"
"$PYTHON_BIN" scripts/pages/cold.py "$CONDITION"
scripts/pages/prefault "$PAGE_MODE" "$PREFAULT_CPU" "$CODE_NODE" \
  "$CONDITION/segments.tsv" "$CONDITION/files" \
  "$CONDITION/prefault.tsv" 1
```

`prepare.py` 生成文件身份、路径清单和执行段清单。`cold.py` 只处理本次副本。它运行后到 `prefault` 之间，不再扫描副本字节，以免重新把页面读入缓存。最后一个参数 `1` 要求冷页检查。

将生成目录写入配置：

```bash
CODE_PAGE_CONDITION=/path/to/prepared_condition
CODE_PAGE_MODE=4k
CODE_PAGE_NUMA_NODE="<code_node>"
CODE_PAGE_COVERAGE_POLICY=strict
CODE_PAGE_RESIDENCY_POLICY=strict
```

切换到 `64k` 时准备独立的条件副本，不让两个正在运行的条件共享同一批被重新预加载的 inode。64KB 条件还要求执行文件 mTHP 功能已具备；工具不会替使用者自动改变共享内核开关。

### 4.2 验证页条件

在运行前后保留快照，离线检查：

```bash
"$PYTHON_BIN" scripts/pages/verify.py \
  --before "$BEFORE_SNAPSHOT" --after "$AFTER_SNAPSHOT" \
  --identity "$CONDITION/identity.json" --mode "$PAGE_MODE" \
  --node "$CODE_NODE" --coverage-policy strict \
  --residency-policy strict --output "$PAGE_CHECK"
```

应核对文件哈希与 inode、可执行映射覆盖、实际 folio、NUMA 归属，以及测试前后是否漂移。文件边界、小库、匿名可执行代码及运行时生成代码分别统计；不能把准备命令成功解释为全部页面验收通过。当前页面检查器接受节点编号 0–3；其他拓扑需要先适配校验器。

`observe` 只记录对应属性，不能替代 `strict` 验收。若启用 `code_guard.so` 防止后续代码页合并，所有对照条件使用相同的 guard，保留其身份，并核验其实际加载。

### 4.3 匿名 THP

带配套进程内控制的代码使用 `ANON_THP_MODE=off|on`。`off` 要检查目标进程 `THP_enabled=0` 且 `smaps_rollup` 中 `AnonHugePages=0`。`on` 只允许 THP，不保证全部匿名页成为大页；报告实际匿名大页覆盖率及对应大小。

匿名 THP 与文件代码页是两个独立维度。不要通过全局修改 THP 来代替任务进程内控制。[Linux THP 文档](https://docs.kernel.org/admin-guide/mm/transhuge.html)

## 5. 控制缓存分配

### 5.1 L3

提供 `l3_cache_limit.sh` 的配套工具使用 resctrl，并将 `L3CODE`、`L3DATA` 设置为相同的低 N 位掩码。它改变目标任务允许使用的缓存分配范围，不保证缓存占满，也不自动改变 BIOS 的共享／Private 模式。

先检查 resctrl 的资源、域、有效 mask、最少连续位和现有组。该工具中的平台边界为 28 个有效位；其他硬件须重新核实，不能把 28 当通用常数。[resctrl 接口说明](https://docs.kernel.org/filesystems/resctrl.html)

在工具目录执行，`WORKER_PID` 必须是已核对的宿主 PID，`GROUP` 使用本次唯一名称，`WAYS` 在平台支持范围内：

```bash
bash l3_cache_limit.sh set --pids "$WORKER_PID" \
  --l3-ways "$WAYS" --group "$GROUP"
bash l3_cache_limit.sh status --group "$GROUP"
```

采集前后检查所有实际域的 CODE/DATA mask，以及 Worker 全部 TID 的组归属。API、Engine、客户端是否加入组必须按实验定义明确。新产生的线程也要检查，不能只保存一次 PID 写入记录。

恢复与删除本次组：

```bash
bash l3_cache_limit.sh reset --group "$GROUP"
bash l3_cache_limit.sh delete --group "$GROUP"
```

`reset` 使用首次修改前保存的值；不要删除恢复状态后再尝试恢复。保留其他组和原挂载状态。路数换算成 MiB 前，必须确认该平台每个共享域的有效容量及每路容量。

### 5.2 L2 指令／数据分配

L2 专项通过配套寄存器工具与控制器操作，不属于 resctrl L3 命令。使用前必须确认 CPU 型号、共享 L2 域、寄存器语义、可写位和最少保留路数。

有效流程是：逐目标核读原值 → 修改已验证的字段 → 目标与对照核读回 → 小规模行为检查 → 业务采集 → 恢复原值并读回。读写核范围必须显式指定，避免工具默认作用于全部 CPU。

当前受限数据分配方法保留指令分配能力，只控制允许的数据分配位。它不是 I/D 互斥切分，也不能根据 mask 字面值直接断言精确有效容量。文档不提供脱离平台校验的寄存器常量；跨平台迁移应先完成控制工具的适配和行为验证。

## 6. 切换推理与编译条件

| 条件 | 设置方法 | 必须检查 |
| --- | --- | --- |
| 异步调度 | `SERVER_FLAGS="--async-scheduling"` 或 `"--no-async-scheduling"` | 实际服务 argv 和 Runner 日志 |
| Eager | 服务参数加入 `--enforce-eager` | 实际执行路径；八阶段的 Full Graph qualifier 不适用 |
| Full／Piecewise Graph | 使用配套 vLLM 的编译与 Graph 配置 | 实际捕获模式及请求命中的图；不能仅凭启动成功判断 |
| Prefix cache | `PREFIX_CACHING_FLAG` | 请求是否复用前缀，以及输入复用策略 |
| PGO／LTO | 切换已构建的解释器／库产物 | 构建配置、源版本、二进制哈希和运行加载身份 |
| workspace／Graph 节点干预 | 配套实验程序与环境参数 | 算法、图节点及依赖是否一起变化；先验证输出 |

编译对照通过 `PYTHON_BIN`、`VLLM_BIN` 和匹配环境选择产物，不能只替换命令行名字。PGO 应记录训练负载，LTO 应记录编译器及链接选项；关闭某项优化后，其余构建条件保持一致。

更换服务参数、二进制、放置或页条件后，重新启动服务并完成预热。已有 CUDA Graph、算法缓存、模型内存和动态库加载状态不能靠修改环境变量原地刷新。

## 7. 预热、重复与统计

一次服务会话内的多个 Decode 不是多个独立实验。对照重复以“独立运行及其完整条件”为单位，并分别保留请求级和 Decode 级分布。

1. 固定预热层次。Benchmark 内部预热、每组预热、会话预热不可混为同一个计数。
2. 固定请求数据；常驻客户端的 `inputs_sha256` 可用于检查输入是否一致。
3. 比较顺序交错，例如 A、B、B、A，降低随时间漂移的影响；记录顺序和重复编号。
4. 先看请求失败、token 数和条件检查，再比较性能。
5. 同时保留均值、中位数、P95、样本数和异常记录；不为了趋势单调删除样本。

相对变化使用 `(条件值 - 基线值) / 基线值 × 100%`。基线为 0 或缺失时不计算。阶段比例按 [第三份文档](03_PMU与计时.md) 的聚合规则计算，先分别完成每次运行的统计，再比较独立运行，避免样本更多的运行获得隐含权重。

TTFT 是客户端发出请求至首个输出的时间；TPOT 按每请求 `(E2E - TTFT) / (输出 token 数 - 1)` 计算；ITL 统计相邻流式输出间隔。吞吐依赖测量窗口和并发条件。阶段 CPU 耗时下降，不自动意味着 TPOT 或吞吐提高。

存在 PMU、SPE 或密集探针的请求与干净 Benchmark 分开报告。机制测试先确认代码路径和数值正确性，性能测试再用无探针请求验证时延与吞吐。

## 8. 保存最小复现材料

每次结果应能回答：使用了什么代码和二进制、请求是什么、条件是否真正生效、哪些记录进入统计、是否完成恢复。保留实际命令、配置、模型与软件身份、原始计数、Benchmark 明细、条件前后检查和汇总。大型文件保留策略见 [使用指南](01_使用指南.md)，原始 SPE 与匹配 ELF 的要求见 [采样指南](04_采样与Trace.md)。
